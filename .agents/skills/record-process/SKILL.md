# 개발 과정 기록

실제로 한 일과 확인 가능한 근거를 짧게 연결한다. 평가자가 좋아할 이야기나 서술형 모범답안을 만드는 작업이 아니다. 기록만으로 참가자의 이해도·주도권·합격 가능성을 평가하지 않는다.

## 범위와 기록 위치
- 참가자의 해석·승인 경계를 따른다. 도구함 정비와 실제 과제 해결은 구분한다. 기록 요청은 코드 수정·테스트 실행·추가 개발의 승인이 아니다.
- 오버엔지니어링하지 않는다. 현재 요청에 필요한 자료만 읽고, 별도 기록 시스템·패키지·MCP·전체 대화 수집·상시 감시·자동 커밋을 만들지 않는다.
- 실제 과제에서 지정한 협업·과정 문서를 우선한다. 기존 문서에 담을 수 있으면 새 파일을 만들지 않는다. 참가자가 지정한 경로가 다음 우선이며, 둘 다 없을 때만 실제 프로젝트의 `docs/PROCESS_LOG.md`를 쓴다. 도구함 내부에는 실제 기록을 쓰지 않는다. INDEX는 만들지 않는다.
- 단일 정리 요청은 이번 기록만 갱신한다. 이후 단계마다 계속 갱신하려면 그 운영 방식에 대한 참가자 지시가 있어야 한다. 매 명령·대화마다 기록하지 않고 범위 확정, 핵심 흐름 연결, 중요한 선택·수정, 실제 검증, 제출 준비 같은 변화만 남긴다.
- 여러 세션이 작업하면 기록 문서의 작성자를 한 세션으로 정하고 다른 세션은 근거가 있는 짧은 인계만 전달한다. 대화·로그가 자동 공유된다고 가정하지 않는다.

## 사실과 근거 확인
- 현재 접근 가능한 참가자 지시, 전달받은 담당자 답, 기존 문서, 관련 변경 내역·실행 출력만 필요한 범위에서 읽는다. 다른 대화·개인 세션 폴더를 무차별 검색하지 않는다.
- 출처를 구분한다: 과제 요구 / 참가자가 전달한 담당자 답 / 참가자 선택 / AI 제안 / AI 실행 / 참가자 직접 확인. 담당자 대화를 직접 볼 수 없다면 전달 범위만 기록한다.
- AI 제안은 참가자의 선택이 아니다. “좋아” 같은 승인은 당시 대상 범위와 연결한다. 승인 출처가 없으면 미확인으로 남기고, 참가자가 이유를 말하지 않았다면 AI의 추천 이유와 분리한다. 모든 사소한 기록 때문에 승인을 다시 받지는 않는다.
- Skill 파일을 읽음, 지침을 실제 적용함, 설치·자동 인식됨을 구분한다. 역할 이름만 보고 사용했다고 쓰지 않는다. 무엇을 위해 참조했고 어떤 결과를 채택·수정·거절했는지 근거가 있는 범위만 적는다.
- Git 로그는 커밋된 변화만, diff는 확인한 변경만 증명한다. 코드 존재는 실행 성공을 증명하지 않는다. 정확한 순서·시각·이유를 모르면 지어내지 않는다. 사후 재구성이면 ‘사후 재구성’과 확인 가능한 범위를 표시하고 기록 시점과 실제 발생 시점을 구분한다.
- 문서와 현재 상태가 충돌하면 불일치와 근거를 남긴다. 과거 실패나 선택을 지워서 처음부터 올바르게 진행한 것처럼 만들지 않는다. 실제 잘못된 기록은 정정 사유를 붙여 바로잡는다.

## 최소 기록
먼저 현재 목표·승인 범위와 마지막 확인 상태를 몇 줄로 적고, 의미 있는 변화마다 아래 항목을 필요한 만큼 남긴다. 전체 체크리스트를 매번 복사하거나 빈 칸을 채우기 위해 내용을 만들지 않는다.

| 항목 | 남길 내용 |
|---|---|
| 단계·순서 | 무엇을 먼저 했고 다음에 무엇을 했는지, 순서를 선택한 이유와 출처 |
| 요청·위임 | 참가자가 맡긴 범위, AI가 실제 수행한 일, 참가자가 직접 한 일 |
| 판단 | 선택한 방법·대안·이유·포기한 점, 제안자·결정자·확인된 승인 출처 |
| Skill 활용 | 참조한 Skill과 목적, 적용 결과, 채택·수정·거절한 부분과 확인 근거 |
| 구현 | 관련 파일, 실제 연결 범위, 임시 데이터·stub·가정·미구현 구분 |
| 검증 | 입력·독립적인 기대값 출처·실제 결과·실행 주체·근거 위치·상태 |
| 남은 사항 | 미확인 규칙·미실행 검사·한계·사용 영향·승인된 다음 작업 |

간단한 항목은 한 문단으로 충분하다. 상세 요구사항·결정·테스트 기록은 요약과 파일 위치로 참조하며 같은 내용을 별도 문서에 반복하지 않는다. 기존 제출 형식이 있으면 그 형식에 맞춘다.

## 검증 주장과 기존 Skill 연결
- [requirements-planning](../requirements-planning/SKILL.md)은 무엇을 만들기로 했는지, [verify-work](../verify-work/SKILL.md)는 어떤 기대값으로 실제 확인했는지의 기준이다. 이 Skill은 그 사이의 순서·판단·근거를 연결한다. 참조만으로 해당 Skill을 실행하거나 범위를 확대하지 않는다.
- 구현 상태와 검증 상태를 분리한다. 검증은 `PASS / FAIL / NOT RUN / BLOCKED`로 적고 대상 버전·검사 범위를 붙인다. 계획·탁상 시뮬레이션·코드 읽기는 실제 기능 테스트 통과가 아니다.
- 제공된 테스트와 AI 추가 테스트, AI가 실행한 검사와 참가자의 직접 확인을 구분한다. 직접 확인했다는 참가자의 말이 없으면 그렇게 기록하지 않는다. 수정 전 통과를 수정 후 통과로 옮기지 않는다.
- 실제 출력·로그가 없으면 ‘실행했다고 보고됨 / 출력 미확인’처럼 근거 수준을 밝힌다. 일부 검사 통과를 서비스 전체의 정확성·보안·최적성 보장으로 확대하지 않는다.
- 빠진 근거는 미확인으로 남긴다. 새 테스트가 필요하면 확인할 입력·기대 결과를 제안하되 기록 요청만으로 실행하거나 코드를 고치지 않는다.

## 출력·보안·마무리
- 어떤 파일을 갱신했고 중요한 판단·미검증이 무엇인지 짧게 알린다. 참가자 확인이 필요한 실제 불일치나 중요한 승인 누락만 짚는다. 서술형 정답을 대신 작성하거나 참가자가 이해했다고 결론내리지 않는다.
- 시험 문제·담당자 대화·코드·로그·개인정보·인증정보는 공개 도구함, GitHub, 외부 서비스에 업로드하지 않는다. 기록은 허용된 과제 작업공간에만 보관한다. 원문·비밀 값은 불필요하게 복사하지 않고 안전한 근거 위치로 참조한다.
- 외부 인증용 브라우저·웹뷰·팝업·숨긴 GUI를 열지 않는다. 새 로그인·기기 코드·MFA·수동 설정을 요구하지 않는다. 기존에 허용된 비대화형 CLI 인증만 사용하고, 없으면 해당 작업만 BLOCKED로 남긴다. 기록을 위해 인증·설치·전역 설정을 변경하지 않는다.
- AI 사용이 금지된 후속 서술형 단계에서는 사용하지 않는다. 기록 열람 가능 여부 역시 실제 시험 규정을 따르며 이 Skill이 허용을 보장하지 않는다.
