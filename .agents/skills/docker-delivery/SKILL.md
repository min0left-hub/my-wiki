# Docker 제출 준비와 검증

## 요청 범위
AGENTS.md의 시작·승인 경계를 따른다. 설명·조건 확인만 요청했으면 파일 작성·다운로드·실행을 시작하지 않는다. 요청된 범위의 패키징과 필요한 검증만 진행하고 앱 기능·프레임워크·DB·Compose 서비스를 임의로 늘리지 않는다. 과제에서 요구하지 않은 이미지 파일·문서·서비스를 추가하지 않는다.

## 터미널 안에서만 수행
- 제공된 시험 환경의 터미널 명령과 로컬 HTTP 검사만 사용한다. 외부 브라우저·새 창·Docker Desktop·GUI·로그인 페이지를 열지 않는다. 사용자에게 로그인·설치·클릭·수동 설정·브라우저 검증을 요구하지 않는다. 웹앱 자체의 로컬 테스트 계정/API 인증은 과제에서 허용한 테스트 범위 안에서만 수행하며 외부 계정 로그인과 구분한다.
- docker login, 외부 레지스트리 push, Docker Hub 게시, 클라우드 배포, 개인 토큰·API 키 입력을 하지 않는다. 외부 업로드는 패키징·검증에 필요하지 않다.
- 필요한 기반 이미지·패키지는 시험에서 허용한 출처와 네트워크 범위가 확인된 경우에만 터미널의 pull/build·패키지 명령으로 받는다. 터미널 다운로드도 외부 네트워크 요청이라는 사실을 숨기지 않는다. 외부 이미지를 인증 없이 받을 수 있다는 보장은 하지 않는다.
- Docker가 없거나 데몬 접근·다운로드가 차단되면 Docker Desktop 설치·실행, OS/WSL 변경, sudo·권한 확대, 보안 설정 변경, 감독·접속 제한 우회로 해결하지 않는다. 사용자에게 조치를 떠넘기지 않고 가능한 파일 작성까지만 마친 뒤 실제 오류와 미검증 항목을 짧게 보고한다. 인증 요구가 나타나면 중단한다.
- 같은 원인으로 반복 재시도하지 않는다. 필요한 로컬 원인 확인 후 허용된 작은 수정이 있으면 제한적으로 재검증하고, 해결할 수 없는 환경 문제는 차단으로 남긴다.

## 작성 순서
1. **제출 계약:** 실제 과제 README에서 요구하는 파일명, Dockerfile/Compose/이미지 파일 중 제출 형식, 빌드·기동 명령, 포트, 환경 변수, 데이터 저장·재시작 조건을 확인한다. 모르는 제출 형식을 추측하지 않는다. 기존 설정이 있으면 필요한 부분만 고친다.
2. **실행 환경:** 제공된 docker version/info와 필요한 경우 compose version으로 클라이언트와 데몬 사용 가능 여부를 터미널에서 확인한다. 버전 출력만으로 빌드 가능이라고 하지 않는다. 인증 정보·전체 개인 설정·비밀 환경 변수는 출력하지 않는다.
3. **최소 패키징:** 현재 프로젝트에 맞춰 Dockerfile과 필요한 .dockerignore를 작성하고, Compose는 과제가 요구하거나 실제 구동에 필요한 경우만 사용한다. 지원되는 런타임·의존성 잠금 파일·빌드 산출물·시작 명령을 일치시킨다. 허용된 기반 이미지와 파일만 사용하고 비밀 값·개인 설정·Git 인증·개인 경로를 이미지에 넣지 않는다. 과제 데이터는 제출 지침이 허용하는 포함·마운트 방식으로 처리한다.
4. **접속·저장:** 컨테이너 내부 서버가 요청을 받을 주소와 실제 포트를 확인한다. EXPOSE만으로 호스트 포트가 연결된 것으로 보지 않는다. 검증 포트는 로컬 루프백에 연결하고 과제 채점용 실행 방식과 구분한다. 사용자 데이터가 이미지에 고정되거나 컨테이너 재생성 때 사라지는지 확인하고 요구된 볼륨/저장 경로를 적용한다. 기존 사용자 저장소를 테스트로 덮어쓰지 않는다.

## 실제 검증
- 터미널에서 지정 방식으로 이미지를 빌드한다. 빌드 로그·종료 코드를 확인하고 파일 존재만으로 성공이라고 하지 않는다.
- 새 테스트 컨테이너/프로젝트 이름과 격리 데이터로 실행한다. 사용자의 기존 서버·컨테이너·볼륨은 종료·삭제하지 않는다. 컨테이너 실행 상태와 로그, 실제 앱 포트의 HTTP 응답을 확인한다.
- 호스트에서 별도로 실행 중인 개발 서버를 잘못 검사하지 않도록 테스트 컨테이너와 연결 포트를 대조한다. 컨테이너는 제출 파일과 명시된 환경/마운트만으로 실행되어야 하며 개인 PC 경로·미제출 코드에 의존하지 않아야 한다.
- 허용된 로컬 API/CLI로 핵심 흐름을 검사한다. 예: 테스트 로그인 → 데이터 읽기/업로드 → 처리 → 결과 조회. HTTP 200이나 로그인 HTML 반환만으로 기능 통과라고 하지 않는다. HTML·정적 자산과 데이터 응답을 구분한다.
- 재시작·컨테이너 재생성 후 보존은 과제 요구에 해당할 때 격리된 테스트 저장소에서 확인한다. 브라우저 렌더링·실제 클릭을 하지 않았다면 화면 검증은 미실행으로 남기며 사용자에게 클릭을 요구하지 않는다. 금지된 화면 자동 조작을 대신 사용하지 않는다.
- 이미지 tar 제출이 실제로 요구되거나 별도 승인된 경우에만 로컬 save로 내보내고, 원본 이미지와 다른 테스트 태그로 load·실행해 제출 파일의 복원을 확인한다. 레지스트리에 올렸다 다시 받는 검증은 하지 않는다. 로컬 복원은 다른 PC에서 직접 실행한 것과 같다고 보고하지 않는다.
- 테스트 정리는 이번 작업이 만든 자원만 대상으로 한다. 전역 prune, 기존 볼륨 삭제, 원본 데이터 초기화를 하지 않는다. 이미지 파일·구성 파일·이미지 실행은 각각 구분해서 확인한다.

## 보고와 한계
실제 과제 지정 문서 또는 기존 검증 문서에 파일·이미지 식별자, 빌드/실행/검사 명령, 포트·저장 방식, 실제 결과·종료 상태, 미검증·차단 이유를 짧게 기록한다. INDEX나 별도 보고서를 의무 생성하지 않는다. 읽기 전용 요청이면 대화로만 보고한다.
[verify-work](../verify-work/SKILL.md)의 근거·실행 구분 원칙을 참고하되 외부 창·사용자 수동 조작 금지가 우선한다. 설정 작성 완료, 빌드 통과, 컨테이너 실행, 핵심 기능 검사, 이미지 파일 복원, 다른 환경 직접 실행은 서로 다른 상태다. 수행하지 않은 검증을 완료라고 쓰지 않는다. 이 Skill은 Docker 설치나 타 PC 실행·규정 적합성을 보장하지 않는다.
