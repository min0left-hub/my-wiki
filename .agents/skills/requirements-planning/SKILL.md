# 경량 요구사항 기획

## 인증은 비대화형 터미널로만
- 외부 서비스 인증을 위해 브라우저·웹뷰어·새 창·팝업·Docker Desktop 등 GUI를 절대 열지 않는다. 숨긴 GUI 자동 조작도 하지 않는다. 사용자에게 링크 방문·로그인·기기 코드 승인·MFA 입력·클릭·수동 설정을 요구하지 않는다.
- 요청된 서비스에 이미 제공·허용된 인증 세션과 비대화형 터미널/CLI 방식만 사용한다. ‘백그라운드 인증’은 기존 허용 인증으로 명령을 실행한다는 뜻이며, 사용자 몰래 새 로그인·계정 연결·권한 확대를 하거나 제한을 우회한다는 뜻이 아니다.
- 인증 창을 자동으로 여는 명령은 실행하지 않는다. 공개 저장소는 로그인 없이 정확한 HTTPS 주소로 받고, 필요할 때 그 명령에만 credential helper를 비활성화한다. 404를 곧바로 로그인 문제라고 판단하지 않는다. 전역 인증 설정을 바꾸거나 개인 비밀 값을 출력·복사·저장하지 않는다.
- 브라우저 승인·새 자격증명·권한 변경 없이는 진행할 수 없으면 해당 작업만 중단하고 실제 원인과 미실행 범위를 보고한다. 자동 인증 성공을 보장하지 않고 반복 재시도하지 않는다. Docker login·외부 업로드 등 기존 금지는 유지한다.
- 개발 중인 과제 앱 자체의 가상 계정 테스트는 외부 서비스 인증과 구분한다. 허용된 로컬 API/터미널 검사로 수행하며 외부 인증 창을 열지 않는다.

## 요청 범위와 과도한 설계 금지
- 참가자가 요청·승인한 작업만 수행한다. 읽기·검토·기획·시나리오 작성·실행·수정의 범위를 구분하고, 다음 단계로 임의로 넘어가지 않는다.
- 요청한 결과를 만족하는 가장 단순한 방법을 사용한다. 요청하지 않은 기능·추상화·범용 프레임워크·리팩터링·패키지·MCP·외부 연결·추가 문서를 임의로 도입하지 않는다.
- 요청 범위에 필요한 통상적 편집·실행·검증과 기존에 합의한 기록 갱신만 진행한다. 전체 테스트·분석을 불필요하게 반복하거나 무관한 파일까지 조사·수정하지 않는다.
- 범위 밖의 추가 작업이 꼭 필요하면 이유·영향·최소 대안을 짧게 설명하고 승인 전에는 실행하지 않는다. 승인된 동일 범위의 통상 작업은 반복 확인 없이 계속한다.

Superpowers brainstorming의 맥락·질문·대안 비교 방식을 참고한 자체 Skill이며 원본 설치본이 아니다.

## 시작 조건
AGENTS.md의 승인 경계를 따른다. 참가자 해석과 기획 정리 요청이 없으면 문서를 만들지 않고 기다린다. 기획 작성 승인은 구현 승인이 아니다.

## 절차
1. 참가자의 해석과 실제 README·제공 데이터·전달된 담당자 답변을 비교한다. 전달되지 않은 대화를 안다고 가정하지 않는다.
2. 필수사항은 명시된 출처를 붙인다. 업무 담당자와 확인한 내용, 참가자 결정, AI 제안을 구별한다. 담당자 미정 사항을 별도로 표시하고 애매한 조건이나 AI 제안을 필수로 승격하지 않는다.
3. 우선사항은 제한 시간과 핵심 흐름에 맞춰 제안하고 참가자 확정 여부를 표시한다. 먼저 만들 것과 단순 권장 기능을 혼동하지 않는다. 추가 기능을 제안할 때 남은 필수사항과 남은 시간을 확인해 우선순위를 제안한다. 참가자가 이미 승인한 선택을 임의로 취소하지 않는다.
4. 미확인사항은 결과를 바꾸는 질문만 남긴다. 업무 규칙은 담당자에게, 구현 대안은 장단점과 함께 참가자에게 제시한다. 명확한 요구를 다시 묻지 않는다. 담당자가 미정이라고 한 규칙은 대안과 영향을 설명하고 참가자의 선택·이유를 기록한다. 미정이라는 이유만으로 특정 알고리즘이나 기능을 필수로 추가하지 않는다.
5. 필요할 때만 2개 정도의 구현 대안을 비교한다. 도구 설치·복잡한 구조를 기획의 기본값으로 두지 않는다.
6. templates/REQUIREMENTS.md를 참고하되 실제 과제가 요구하는 문서·경로에 우선 기록한다. 지정이 없을 때만 wiki/REQUIREMENTS.md를 사용한다. 문서에 승인 상태를 표시한다. INDEX는 만들거나 갱신하지 않는다.
7. 참가자에게 필수·우선·미확인·제외 범위와 성공 조건을 짧게 보여주고 구현 방향 승인을 기다린다. 구현 요청이 이미 명확하게 주어졌고 핵심 조건도 확인됐으면 그 범위의 기존 승인을 존중한다.

담당자의 새 답을 받으면 기존 요구사항·결정과 비교해 변경된 규칙과 출처, 구현 영향, 검증 영향을 갱신한다. 해결된 미확인 표시는 정리하되 이전 결정과 변경 이유는 추적 가능하게 남긴다. 다른 자료와 충돌하거나 결정 권한이 불명확하면 임의로 확정하지 않는다.

성공 조건은 ‘입력/사전 상태 → 동작 → 관찰할 결과’로 적고 검증은 아직 수행하지 않았다고 구분한다. 산출물은 짧은 요구사항 문서이며 완성 답안·구현 코드가 아니다.

## 문서 상단의 동작 흐름과 진행 상태
요구사항 문서의 제목 바로 아래에 ‘프로그램 동작 흐름·진행 현황’을 둔다. 사용자 관점의 순서(입력 → 조회/선택 → 처리 → 저장/출력)를 과제에 맞춰 짧게 정리하고 각 단계에 관련 요구 ID·성공 조건·구현 상태·검증 상태·근거를 연결한다. 고정된 화면이나 기능을 새 필수사항으로 추가하지 않는다.
구현 상태는 미착수/진행 중/구현됨/확인 불가, 검증 상태는 미실행/통과/실패/차단으로 분리한다. 코드나 실행 근거를 확인하지 못했으면 추정해서 완료로 바꾸지 않는다. 아직 기획 단계이면 미착수·미실행으로 둔다. 기획 요청만으로 테스트를 실행하지 않는다.
업무 흐름·코드·검증 결과가 바뀌고 문서 갱신이 허용된 경우 관련 행을 최신 근거로 갱신한다. 검증 결과를 갱신할 때는 verify-work의 결과와 연결한다. 별도 INDEX나 중복 진행 문서는 만들지 않는다.

## 웹서비스 과제의 기획
웹서비스 과제이면 아래 중 실제 요구에 해당하는 항목만 짧게 정리한다. 자료에 답이 있으면 다시 묻지 않고 근거를 연결한다. 로그인·회원가입·관리자·게스트·내보내기·업로드를 모든 서비스의 필수 기능으로 만들지 않는다. 비로그인 방문자와 로그인한 일반 사용자를 구분하고, 미정은 미정으로 남긴다.

| 항목 | 정리할 기준 |
|---|---|
| 목적·범위 | 사용자 문제, 핵심 흐름, 필수·선택·제외, 완료 조건 |
| 사용자·인증 | 실제 역할, 로그인 필요 여부, 제공 계정·가입 요구, 실패·로그아웃·인증 만료. 앱 자체 로그인과 외부 서비스 인증은 구분 |
| 권한 | 역할별 화면·기능, 본인/전체 자료 범위, 조회·등록·수정·삭제·승인 권한. 버튼 숨김뿐 아니라 서버 요청에서도 금지 동작을 거부 |
| 화면·동작 | 화면 진입·이동, 표시 정보, 입력 → 검증 → 처리 → 저장 → 결과, 처리 중·빈 결과·오류·권한 없음 표시 |
| 데이터·업무 규칙 | ID와 자료 연결, 필수값·범위·계산·포함/제외·시간·상태 전이. 원문/전달받은 담당자 답/참가자 결정/AI 제안 구분 |
| 저장·변경 | 원본·적용본·설정·결과의 구분, 새로고침·재시작 보존, 입력 변경의 재계산/무효화/이전 결과 표시, 실패 시 상태 |
| 예외·보호 | 해당되는 잘못된 입력·중복 요청·충돌·저장 실패, 불필요한 개인정보·비밀 값 노출 방지 |
| 실행·제출 | 실제 환경·시작 명령·포트·저장 경로·Docker 요구·문서명과 외부 연결 제한. 사소한 기술 선택은 최소 대안으로 제안 |
| 검증 조건 | 기능별 정상·경계·오류 입력과 출처 있는 기대값. 기획 단계의 조건과 실제 실행 결과를 구분 |

### 데이터 업로드 방식
업로드가 요구될 때만 다음을 기존 요구사항에 기록한다.
- 누가 어떤 화면에서 어떤 파일 형식·필드·단위·문자 인코딩·파일 수/크기 범위를 입력하는지, 단일 파일/관련 파일 묶음인지 정리한다. 지정되지 않은 제한 수치를 임의로 업무 규칙으로 확정하지 않는다.
- 파일 선택 → 읽기/파싱 → 내용 검증 → 미리보기/오류 안내 → 적용 중 실제 필요한 흐름을 정한다. 검증과 운영 데이터 적용을 구분하고 검증 실패 자료가 기존 정상 자료를 덮어쓰지 않도록 한다.
- 빈 파일·필수 열·자료형·허용 범위·중복 ID·파일 간 참조·날짜/시간 등 해당 검증 조건과 오류 위치/사유 표시를 정리한다. 정정·중복·부분 적용·전체 거부의 업무 정책이 미정이면 확인하고, 임의 삭제·보정·부분 적용을 하지 않는다.
- 재업로드 시 추가/교체/병합 정책, 저장 위치·적용 버전과 결과 재생성 여부를 확인한다. 업로드 버튼만 있는 것과 실제 서버 저장·적용이 연결된 것을 구분한다.
- **업로드 데이터의 실제 검증은 [verify-work](../verify-work/SKILL.md)를 참조한다.** 확정 스키마·업무 규칙에서 정상·경계·오류 자료와 기대값을 정하고, 허용된 실행 범위에서 적용 성공/거부·기존 자료 보존을 확인한다. 여기서는 기획 조건만 정의하며 검증 참조가 테스트 실행·코드 수정의 승인은 아니다. 검증만 요청이면 수정하지 않는다.
- 이 항목의 업로드는 과제 앱 내부의 허용된 로컬 입력 기능이다. 시험 자료를 GitHub·외부 저장소로 보내는 권한이 아니다.

### Export·다운로드 방식
내보내기가 요구될 때만 사용자 목적과 필수 형식을 먼저 확인한다.
- 전체/현재 필터/선택 항목/게시 결과 중 어떤 범위를 누가 받을지, 표시할 열·순서·단위·기간·적용 버전·파일명·인코딩을 정한다.
- 사용자용 결과 내보내기와 내부 백업·복원은 별개다. CSV·JSON·엑셀·PDF 등 모든 형식을 자동 추가하지 않으며 복원 기능도 별도 요구가 있을 때만 포함한다.
- 권한에 맞는 데이터만 포함하고 내부 메모·타인 정보·인증 값은 불필요하게 내보내지 않는다. 빈 결과·생성 실패·이전 버전 결과를 어떻게 안내할지 정한다.
- 성공 조건은 ‘다운로드 버튼 존재’가 아니라 파일 내용·행 수·한글·구분자·값/자료형·화면 필터와 일치 여부로 적는다. 실제 검증은 verify-work를 참조하며 파일 작성/실행 승인을 구분한다. 로컬 다운로드와 외부 업로드·공개를 혼동하지 않는다.

## 같은 문서를 참조하는 병렬 작업
동일한 요구사항 MD와 이 Skill을 여러 세션이 읽으며 서로 다른 작업을 병렬 수행할 수 있다. Skill을 따로 만들거나 모든 작업을 순차로 진행할 필요는 없다. 세션별 대화·파일 변경을 자동 공유한다고 가정하지 않는다.
- 참가자가 지정한 담당 범위와 요청 모드를 존중한다. 예: A는 데이터 구조·규칙 정리, B는 확정된 역할·화면의 기본틀 구현. B의 실제 구현에는 별도 또는 기존의 명확한 구현 승인이 필요하며 기획만 요청했으면 정리까지만 한다.
- 독립적인 일은 동시에 진행하고, 결과가 필요한 부분만 연결 전 최신 기준을 확인한다. 처음부터 모든 설계가 끝날 때까지 불필요하게 대기시키지 않는다.
- 편집할 파일·폴더와 공통 문서 갱신 담당을 정해 같은 파일 동시 수정을 피한다. 공통 문서를 함께 읽는 것은 제한하지 않는다. 공통 기준이 바뀌면 해당 세션에 전달하고 필요한 부분을 다시 읽는다.
- 연결에 필요한 최소한의 필드명·자료형·입출력·오류 표현을 맞춘다. 새 API 프레임워크나 복잡한 계약 문서를 의무로 만들지 않는다.
- 미정 규칙은 상대 담당에게 확인하고 임의 구현하지 않는다. 예시 데이터·임시 처리·미연결 기능은 실제 데이터·완료 기능과 구분한다. 연결 후 관련 전체 흐름을 verify-work 기준으로 확인하며, 기획 요청만으로 그 검증을 실행하지 않는다.
